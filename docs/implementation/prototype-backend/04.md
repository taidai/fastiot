## Implementation and shared-file boundaries

- Reuse `industry.Registry`, its persisted installation record, the existing route/action declarations, and ticket 01/02 authentication/project context. No marketplace, licensing, purchasing, deployment or new control authorization mechanism.
- One engineering-content classifier now drives package dependency pins, import requirements, disable blockers and workbench gates. It includes EnergyUnit/Plant/ResourceGroup and non-tombstoned allocator, plan96, tariff, targets/constraints/PCC configuration. Activation never removes a dependency; ordinary IoT/SCADA and tombstoned configuration do not acquire one.
- Additive snapshot contract: `industry: {id: "ems", version: string, installed: boolean, required: boolean, blocked: boolean}`. `required` describes authorized engineering content plus inherited dependency along its authorization anchors' ancestry; `blocked = required && !installed`. `GET /projects` uses that same dependency determination. Ancestry is used only for a dependency boolean: no additional ancestors/sibling objects are returned or added to `Identity.Anchors`. Cycles, missing/ambiguous ancestry and read failures refuse uncertain operations with generic `503 project_context_unavailable`, not a false no-dependency result.
- Base configuration/control mutations cannot bypass the gate by using a generic route or omitting `X-Fastiot-Project`. Reads, read-only diagnostics, alarm handling, accounts/audit and industry recovery remain available subject to their existing permissions. L3 additionally checks the dependency; L1/L2 keep their existing read-only authorization and validation.
- Generic `/nodes` EnergyUnit/Plant creation and storage-template creation reject absent EMS before creating any object. Pump-house remains available. Activation requires existing `site_settings` permission **and runtime-root scope**; a Site-scoped account cannot disable a hidden sibling Site's dependency. An API read/write lock makes activation exclusive with engineering/control mutations, so disable's in-use check cannot race a new dependency into existence.
- Frontend `industryBlocked` is derived only from `session.snapshot.industry`; no parallel frontend registry. `IndustryPanel` refreshes the shared snapshot after activation and explains that enabling is not purchasing, deploying or control authorization. The toolbar reflects the shared live state and scope/permission gate. Delivery system tabs remain reachable while dependent asset actions are gated.
- Cross-ticket edits are deliberately additive: design `index.vue` and `LiveOverview.vue` only import/wrap their existing body with `IndustryGate`; their internal ticket 03/09 logic is untouched. Delivery `index.vue` adds the gate and IndustryPanel refresh binding, not AccountsPanel logic. `handler.go` adds mutation/snapshot/root-scope/generic-create checks; `resources.go` adds only storage-template and L3 preconditions; `project_context.go` adds inherited dependency determination. No README or other ticket status edits.

- Snapshots refresh on normal workbench load/refresh and after IndustryPanel changes; no new cross-client activation push protocol was added. The server checks each request, including stale clients.
