## Local implementation (2026-11-26)

- The existing `/api/delivery/evidence` ZIP (device ledger, verification records, communication report, alarm statistics, live + latest persisted preflight, per-point mapping differences, audit, effective permission matrix) gains `09-验收证据.json`, a machine-checkable manifest:
  - `format: fastiot.acceptance-evidence`, version, export time and actor;
  - the exporter's scope: admin flag, anchors and effective actions;
  - for each Site the caller may see: the latest version ID and engineering fingerprint, the live preflight status/fingerprint, per-channel address and `evidence_class`, and that Site's append-only deployment records (from ticket 22, each with the three separate applied/acquisition/control flags and the acquisition evidence);
  - statistics provenance: the alarm window and the explicit statement that quality counters are per-process and reset on restart;
  - an explicit disclosure that loopback channels (`127.0.0.1`/`::1`/`localhost`) are `simulation`, non-loopback are `field`, and neither is a physical commissioning signature.
- Scope is enforced before evidence is written: the route requires the `export` action and the manifest iterates only Sites the caller can see; deployment records are read per visible Site only. Secrets are still excluded by the existing point filters.

A viewer account for another Site is refused with 403 (no export action).
- The delivery page keeps its existing 导出验收证据 button and preview/real separation; the preview-mode JSON fixture name is unchanged.

## Explicit limits

- The manifest reports the latest version per visible Site, not an arbitrary historical one; there is no "export a chosen historical version" selector (ticket 23 covers restoring one).
- Statistics stay process-scoped where the runtime is; the manifest states that rather than importing a false day-total.
- Evidence is software/simulator evidence unless the channels are non-loopback, and even then it is not field acceptance; no real devices were contacted.
