- `GET /users` returns only accounts whose complete stored scopes and user edges are within the caller's scope, with effective actions resolved through the existing identity path. Create/update/password-reset enforce scope and grant ceilings; a delegated manager cannot create an administrator, grant actions they lack, move outside their scope, or reset a more privileged account's password.
- `PUT /users/:id` accepts an optional `parent` to change the account's subtree. Existing sessions re-resolve authorization on the next request. A scope move revokes first, then moves and saves, so an intermediate failure cannot broaden access.
- `GET /users/:id/authorization?target=<object-id>[&operation=<operation>]` explains the six matrix columns (overview, command, configure, project publish, account management, audit). It reuses `identityForUser`, the canonical route declarations and `routeAuthorization`/`allows`; it never dispatches an action handler, switches identity or registers a session. Unknown operations and unknown/out-of-scope objects fail closed. Out-of-scope and absent accounts both return generic `forbidden` without account/object detail.

## Deliberate limits

- This is **authorization only**, not “currently executable”: an allow does not bypass capability, dependency, parameter, command-readback or site-safety checks. No physical operation or real-device acceptance is claimed.
- Account range editing supports one subtree per account. Existing mirrored/multi-edge accounts are not silently collapsed; attempted range editing returns `multiple_account_scopes`. Self-demotion/self-range relocation is blocked.
- A storage failure during a range move may leave that account denied until an administrator repairs/resaves it. This is intentionally fail-closed, not a claim of transactional rollback across store operations.
- Admin retains the existing all-actions semantics; empty non-admin whitelist means role defaults, not “deny all”. Read-only roles with no grants remain the deny-all-action option.
