## Persisted declaration and API

`dailyStats` is a JSON node point (empty point key), independent of `easyemsScreen`. It is written only through the Configure-authorized `PUT /api/nodes/<layer-id>/daily-stats-config`; `GET` on the same path reads it. An unconfigured node returns version 0. Example request (identifiers are placeholders):

```json
{
  "version": 0,
  "time_zone": "Asia/Shanghai",
  "energy": {"point_id": "meter-id", "unit": "kWh", "max_gap_seconds": 60, "reset_policy": "discard_interval"},
  "runtime": {"point_id": "run-id", "running_value": 1, "stopped_value": 0, "max_gap_seconds": 60},
  "freshness": {"point_id": "observed-point-id", "max_age_seconds": 60},
  "communication_point_id": "observed-point-id"
}
```

- Each metric is optional; absence yields `unavailable/binding_missing`, never 0. Time zone is required on save; browser time zone and machine `Local` are not used. Duration bounds must be finite, positive and at most 86400 seconds. Both runtime values must be explicitly present and distinct.
- PUT validates the entire document, referenced point types, cumulative unit, layer subtree and identity scope before a single node-point save. The existing node configuration lock serializes compare-version/save; stale versions return 409. Bad declarations do not partially save. Reads recheck every reference. No customer-screen configuration controls were added.
- `GET /api/overview/daily-stats?layer=<id>[&date=YYYY-MM-DD]` returns `layer_id`, `config_version`, server `as_of`, calendar `window` (`date/time_zone/start/end/through`), and `energy/runtime/communication/freshness`. A future or invalid day is rejected when a configured time zone can resolve it. `through` is min(server now, next calendar midnight).
- Metrics carry `value: number|null`, `status: available|partial|stale|unavailable`, typed `reason`, unit, source and observation time/basis. Daily metrics include `covered_seconds`, `coverage` relative to elapsed day, `history_lifetime` and source `retention`. `partial` is only the measured subset, not a complete daily total. Equal valid cumulative samples and valid stopped intervals can yield genuine 0.
- Energy supports one explicitly declared nonnegative kWh cumulative meter. Adjacent good, trusted raw samples with matching configuration stamp and interval no larger than max-gap contribute a delta. Decreases mark reset/rollover intervals as unknown; no post-reset amount is invented. Midnight-crossing pairs are not interpolated. Runtime is a declared sampled-left-state calculation closed by the next valid observation; unknown states/events/gaps prevent contribution, and the last state is never extended to now.
- Communication reuses the runtime channel's five-minute lookback **minute buckets**: `[floor(now-5min), now]`, with attempts and successes, 60-second resolution, platform-poll basis and process-memory retention. It is not lifetime success rate, not exactly a 300-second event window, and not a daily statistic. No attempts returns null. Freshness is server age of the latest trusted good observation (device or successful platform collection/acquisition), not receipt/query/page time. Later invalidation, untrusted metadata or future timestamps cannot become a fresh value.
- `frontend-uniapp/src/pages/overview/daily-stats.ts` exports `DailyStats`, `DailyMetric`, text/detail helpers; `daily-stats-api.ts` exports `loadDailyStats(layerId)`. `OverviewDailyStats` accepts `layer-id` and optional `result`: undefined fetches; null/object consumes the parent's shared result without another query. Parent readers must retain layer/project-generation fencing; the component's own reader fences both and rejects mismatched `layer_id`. It can be consumed by ticket17's summary slot; ticket12 only replaces the four existing daily figures, not trend, alarms or execution regions.

## Deliberate unsupported inputs and retention boundary

- No inferred meter/run semantics from names, power integration, counter-modulus reconstruction, text-state mapping, multi-meter/device aggregation or automatic inheritance of fixed point references. One binding per metric, within the declared layer's actual subtree; missing/unsupported data stays unavailable.
- Runtime history10 is bounded **process memory**, not durable complete-day history. Server restart preserves `dailyStats` configuration but loses those runtime observations. New post-restart segments can be partial; full-day continuity is **not** implemented or claimed. Retention-cap partials expose `retained_history_partial`; queries over 10000 records return `history_limit_exceeded` with null rather than summing a truncated day.
- Persistent SIOT fallback rows currently lack the explicit quality/time-source metadata needed for these statistics. They return `quality_or_time_metadata_missing`; they are not merged into runtime history to manufacture coverage. Durable quality-bearing historical recovery remains an upstream dependency, not a history/aggregate redesign in ticket12.
- Project-package tickets20/21 must carry `dailyStats` engineering declarations and rewrite `energy.point_id`, `runtime.point_id`, `freshness.point_id`, `communication_point_id` on import/copy. This ticket does not alter package boundaries or silently reuse old-site references; the query's scope check rejects references outside the new layer.

## Shared quality-source correction

Real HTTP/browser tests exposed a pre-existing counter defect: a failed read was counted by both `recordLatency` and `recordFailure`, so one successful read plus one failed read showed 66.67%, not 50%. Ticket12 fixes the source at the actual transport-call boundary, with coordinator approval:

- Each read call and each register/coil write call counts once. Connection/transport error counts one failure. Multi-register writes count the calls actually attempted, including early failure; unexecuted I/O (validation rejection/cancellation) counts none.
- Decode failure after a successful transport response still invalidates point quality and affects existing device health counters, but does not invent a failed transport attempt. Existing lifetime health and read-latency counters are retained; rolling-window successful-I/O latency uses the same successful-attempt denominator.
- Buckets use the `RunOnce` clock, not a separate `time.Now` timestamp. Window reads exclude future minute buckets and retain the documented inclusive oldest-minute boundary.
- Public channel tests cover 50%, failed writes, zero attempts, rejected/cancelled I/O, decode failure versus transport success, multi-register writes, future buckets and window expiry; the HTTP test proves an old success outside the window cannot improve a current failed window.
