## Implementation decisions

- L3 remains opt-in. The existing fixed-value, parameter-free Profile command must target a writable `L3_SAFE` point and declare its readback. Declared enum/binary values, current Profile/mapping, bound business Device, point/server semantics, configure **and** command actions, channel/point/business scope, project-industry dependency and explicit confirmation are checked before dispatch. No arbitrary client point, value, retry/fallback or exact-write override is accepted. L1/L2 payloads remain compatible and read-only.
- The existing verification GET returns its current opaque `basis` (Profile fingerprint, mapping revision and physical acquisition configuration). L3 POST requires this basis and a stable caller `request_id`; no server-generated replacement ID. Missing/stale basis is rejected before physical I/O. Profile, mapping and physical changes invalidate recorded evidence.
- Every accepted L3 goes through 07's `command.Manager` and the same durable journal. The canonical intent carries actor/time, `Source=manual`, `Stage=L3`, and `DispatchID=basis`; reuse of an ID also checks this L3 basis. Existing terminal results are returned without consulting device online state or redispatching. Readback waiting uses the canonical deadline, observations, tolerance, clock checks and unknown semantics. No second result engine, protocol-write bypass or automatic fallback was introduced.
- Verification records retain actor/time/reasons, original Profile and mapping version, basis, and canonical device/command/request references. Command state is a projection, not independent confirmation. The shared reuse/runtime exclusion now strips `easyemsAccessVerification` from project export/import/copy/version reuse; field evidence and old command references are not engineering assets.
- AccessStep keeps the prototype's existing L3 section: declared target/value/readback/tolerance/deadline, explicit confirmation, one request identity saved before submission, and a read-only query control after reload or a lost response. Requests are isolated by actor and device. No operation-drawer or bulk UI change. Existing React source contains no L3 verification caller requiring migration.

### Narrow 07 consumer contract: exact declared writes

The shared manager previously clamped a fixed safe value and changed its readback target, allowing a different physical value to pass. `Request.ExactWrites` is a server-set opt-in used by L3: any guard clamp rejects the entire normalized sequence **before** dispatcher invocation. Default false retains existing callers' clamping semantics and byte-compatible v2 identity encoding (the new fingerprint field is omitted when false). True participates in durable fingerprint comparison; both directions of same-ID flag changes conflict. Old journal entries are not rewritten; legacy fingerprints cannot claim the new exact-write guarantee. This does not change rule/state-machine implementations, safety limits or deadlines.
